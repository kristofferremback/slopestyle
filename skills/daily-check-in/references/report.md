# Report and publication

## Judgment and input

Use the helper's `Report` type and `examples/report.v1.json` as the version 1 field contract. The example is synthetic, not a source. A user-facing check-in contains researched real work; use fixtures only for explicitly labelled UI/testing previews. Include all eight coverage entries (`calendar`, `t3`, `vault`, `linear`, `github`, `slack`, `email`, `todos`) and honest status, query window, detail, and next step. Set the report date from `capturedAt` in Europe/Stockholm. Unknown schemas fail; do not improvise a migration. The helper can read early version 1 snapshots with `quickWinMinutes`, showing unknown effort instead of carrying over duration estimates; new input uses `effort` and `quickWin`.

Write for a 30-second overview. Use a short action headline, a one-sentence summary, and brief schedule constraints. Keep item titles and next actions short enough to scan; the page shows Kris’s own work and quick wins first, with every personal task title and next action visible. Expand rows for reasoning and supporting evidence. Use ordered `items`: `must` contains actual hard commitments for today, `aim` is the aggressive but feasible aspirational today list, and `later` preserves the remaining inventory. `rationale` explains the consequence of delay or an explicit exception; `timing` gives actual deadlines, calendar commitments, or `no confirmed deadline`; do not estimate durations. `effort` is XS (tiny action), S (small bounded task), M (several steps), L (substantial work), XL (needs decomposition), or unknown. These are relative effort judgments, never hours in disguise. `you` states Kris's concrete action or `Nothing now`; `others` names the owner and deliverable/confirmed ETA, or says unknown. `quickWin: true` is only for independently finishable, low-setup open actions, normally XS/S. A quick win may lead when its consequences or dependencies warrant it, never because it is short. Preserve blocked outcomes even when only follow-up is possible. Carryover is normal, not a failure.

Separate attention from priority using `attention`: `work` (the default) is a concrete task requiring Kris’s attention, `background` is review or agent work progressing alongside his day, and `unassigned` is an unresolved ownership question. Show background work separately; promote it only when a specific human action stops progress or has a stronger consequence than the main work. Source freshness or PR activity is not priority. Project target dates matter even when individual tickets have no due date. Reconcile acceptance checklists with current delivery evidence before calling them remaining tasks. Prioritize the work Kris committed to, not invented status checks or reviews for every open PR.

Plan from the invocation time, not a full morning if it is already afternoon. Weekday defaults are boat 08:00–08:40, office 08:50–16:00, boat 16:10–16:50, lunch about an hour around noon, standup about 15 minutes at 09:15. Replace these with actual calendar and Kris's corrections; do not double count standup or lunch. Boatwards protects bookings, may include pickup and half-AFK work, and is not automatically a full work block. Offer evening or weekend work only when Kris explicitly elects it that day. Do not insert a fixed reserve percentage. State what slips if the aggressive plan overflows.

Read the previous report before creating input. Keep a stable item ID across T3, Linear, GitHub, and other citations. For each previous open or blocked item, either revalidate it and include the same ID, explicitly close it with `done`/`dropped` plus `closureReason` and `closureEvidence`, or let the helper carry it forward visibly as unrevalidated. Omission is never completion. Same-ID corrections replace the old field values; a superseded item needs explicit closure. Persist decisions by stable ID with `recordedAt`, optional `itemId`, `state`, and `expiresOn` for temporary instructions. Explicitly retire replaced decisions; expired decisions remain history but leave the active view. The helper carries omitted decisions forward.

`notRevalidated` belongs only to stored helper output. When an old item is checked live and reused in new input, remove that field and supply current `plan`, `timing`, `you`, `others`, and evidence. A carried item has no current action offer, even if its older copy had one. Make provenance visible at the claim: use inline `[Jules’s draft · Slack, Sep 29](https://verified-permalink)` links in prose, including You, Others, timing, decisions, and calendar constraints. Link the actual draft, message, note, event, PR, or ticket being referenced, not a homepage or search. Use exact identifiers and a short source/author/date label so Kris can tell where a claim came from without opening it. List each item's primary record first in `sources`; it links the title and appears in the collapsed overview. Distinguish your recommendation from sourced facts, and link the evidence behind its consequence. Every referenced artifact or factual commitment needs its own source link; a general source list does not substitute for inline evidence. Review every reference before publication. If a navigable URL cannot be verified, say `link unavailable` with the exact source ID/path and expose the missing step; never invent a URL or imply an unlocated draft is available. Prose supports only inline HTTP(S) links, with URL spaces/parentheses percent-encoded; other Markdown and raw HTML remain text.

## Publish and host

Use an absolute skill path, for example `CHECKIN_SKILL="$HOME/.local/share/slopestyle/skills/daily-check-in"` after verifying that it exists. The default artifact root is `~/.local/share/galdera-check-in`, outside Git. `--root` is for isolated fixtures. Run `bun "$CHECKIN_SKILL/scripts/check-in.ts" latest` before research, then write draft JSON to a scratch path outside the artifact root. Run `validate --input FILE`; inspect the full input and make uncertainties visible; publish the researched proposal with `publish --input FILE --expected N`, where `N` is the exact latest revision or `0` on first use. Link that first page for discussion. After Kris's corrections, validate and publish a revised page against its latest revision without a separate publication approval. On a stale revision, reload latest and reconcile before retrying. Publish creates an immutable numbered directory with `report.json` and `index.html`; `/` serves the current render and `/archive` links dated revisions. There is no pruning or deletion policy.

For laptop access, run `slopestyle-ports --help`, then from the artifact root run `slopestyle-ports show --app galdera-check-in`. Reuse its `web` service when present. If the checkout has no lease, or its lease has no `web` service and the block is inactive, run `slopestyle-ports claim --app galdera-check-in web`. Read the returned port; a reserved URL is not yet live. A claim can fail when a route or listener already makes the block active. Inspect the existing lease and listener before reusing it, and leave an unknown listener alone. Start `bun "$CHECKIN_SKILL/scripts/check-in.ts" serve --port PORT` with its working directory at the artifact root as a durable background process; save a PID and log there only for the process this workflow started. Verify the `127.0.0.1` listener and that HTTP `/` renders the newly published revision; reuse an existing server only after those checks. Run `slopestyle-ports serve --app galdera-check-in web` from the artifact root for the private Tailscale route, and use its printed URL only after retrieving the current revision through it. Manual check-in invocation authorizes this private laptop artifact and route, not public hosting or upstream writes. If hosting is unavailable, report the exact local artifact path and gap without claiming the URL works.
