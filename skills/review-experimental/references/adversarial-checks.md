# Adversarial checks

Select applicable patterns from the changed responsibilities. Use their concrete sequences to build probes and the behavior matrix. Record the evidence or exact missing dependency; a pattern name alone is not coverage. These are investigation patterns, not predetermined findings: establish a current trigger, independent contract, and actual causal chain before classifying a defect.

## Persisted history and reconstruction

Take a valid historical snapshot, make ordinary edits that remove old entities and create new ones, then restore or replay the snapshot. Exercise the real issuance/validation owner so a fixture cannot bypass its protection. Inspect whether later issuance replaces, prunes or preserves the protecting registry. Repeat with an older related parent/baseline and with both managed and legacy ownership paths. Compare eligibility with the base and disclose stricter behavior when its acceptance is unresolved.

Inventory the complete configuration schema, then compare authored versus restored fields one by one. Include missing optional blocks, inheritance/null values, and records created before the newest snapshot format. Distinguish authored settings from effective execution values. A helper that reconstructs a display is not automatically a lossless write representation; identify exactly what its fallback omits and which historical records reach it.

For each actual removal or replacement, check confirmation text against the destructive effect. Check help and machine-consumed guidance against enabled, disabled and unresolved modes; UI text can be correct in one mode and misleading in another.

## Signals and asynchronous effects

Build a handoff table from each asynchronous state-changing operation: state read before waiting, concurrent operations that can change it, external effect and returned identity, state recorded after waiting, and the later completion or cleanup claim. Place interruption and ordinary concurrent commands on both sides of each distinct handoff. Retry after intent persisted but notification failed; delay a successful response until its earlier state is no longer current. Follow the acknowledged external resource through persistence, reconciliation and cleanup. Close each handoff with a concrete result or an exact missing premise, rather than a collective “cancellation checked” row.

For each signal received during active work, trace the work’s possible settlements and which event schedules another iteration. After finding one failure in a shared owner, enumerate its other callers and settlement modes and test the same failure there; a single example does not establish the consequences for the other entry points. Keep every distinct user consequence visible in the resulting findings. An idempotent intent write alone does not establish reliable delivery.

## External changes and earlier success

After a successful operation, change classification metadata without changing the source: join or leave a group, change its target, or change readiness. Trace both which event reruns work and which consumer invalidates or continues using the earlier successful receipt/status. State a conditional consequence when an external protection is unknown, together with the exact check needed to settle it; do not silently turn that uncertainty into either proof of safety or a proved bypass.

## Ranked, grouped and compared data

Exercise every user preset and every row/column/series axis, not only a generic table. Preserve semantic ordering of time, age, sequence and version axes unless its change is explicit. Compare prior default selection with the new sort, including numeric versus lexical labels and missing ranking operands.

Use disjoint and partially overlapping populations. Trace visible rows, counts and totals independently: what population does each describe, which omitted members remain in totals, and where does the user learn about loss? Exercise more members than each cap and a long history with a short visible window. Count visible versus hidden buckets against packing budgets. Make each compared read substantially larger than its anchor; validate its own budget and the combined result limit.

For search, follow a displayed label through request construction, server matching, returned metadata and controls. Test renamed labels, an unloaded match, enough matches for multiple pages, and the second page. Check offset propagation, total/matched counts, and whether the user can reach every match. Compare every ordering/ranking label with the actual fallback when the requested operand is unavailable.

## Feature and machine interfaces

For each feature-controlled operation, inspect enabled, disabled, pending and failed feature resolution at the client and server. Check schema/tool advertisement against the handler's accepted capabilities in each mode. Identify model/tool changes even when most of the diff is ordinary application code. Read the owning eval policy and account for its specific slices/scenarios, feature variants and default model matrix before reporting validation complete.

## Code and ownership

Compare effect ownership across sibling handlers: which return a result for one coordinator to record, and which hide the same recording inside callbacks? Prefer a consistent owner before recommending more guards. Inspect production-code paragraphing separately from test phases; both are part of the local pass.

When a helper interprets a string as an identifier, path or expression, inspect its validation contract and existing caller protections. A checked type, validation at the owner, or an explicit trusted-input interface can make that ownership visible. Suggest the smallest coherent boundary improvement as style advice when warranted; do not invent an injection exploit where current callers enforce the guarantee.
